## 3. Mobile "stuck / no loading" problem — fixed everywhere (commit `2346729`)

**Cause.** The loading overlay only appeared for sidebar links and sign-out. Edit, Cancel, Save Changes, Filter,
the date pickers and browser Back showed nothing, so on a slow connection the phone looked frozen. The party
and voucher pre-save checks also waited silently, and after Save you landed at the top of a long list with the
success message easy to miss.

  restores; "slow connection" note after 7 s; gives up after 45 s with a clear message.
- `party-check.js` / `voucher-dup.js` show "Checking party…" / "Checking voucher number…".
- Flash messages become a toast pinned to the top of the screen.
- Saving an edit returns to the edited row, highlighted (manager collections/invoices, later employee too).

## 4. Manager can rename a party

- New manager **Parties** page and rename form (`/manager/parties`).
- Plain renaming is dangerous in this app (invoices/payments link to a party by its name text), so
  `PartyRenameService` changes the party **and** re-points its invoices and payments in one transaction, writes
  an audit row, and refuses blank names, clashes with another party, and names already used by orphaned
  history. Only the name changes; code, GST and opening balance stay.
- Tested: balance identical before/after, history moves, rename-back works, other roles are blocked.

## 5. Admin/accountant "Edit Party" now uses the same safe rename

- Before: Edit Party renamed only the party row and **orphaned its whole history** (the KAIF/PRASANG class of

  the combined name, refuses clashes/orphan names with a visible message, and leaves simple edits (phone etc.)

## 6. Admin Collection Map

### 6.1 Goal
A map for the admin: a globe that zooms into Azamgarh and drops a pin for every place a collection was made, so
the Purvanchal spread (north/south/east/west) is visible.

### 6.2 What the data actually looked like (live Neon, checked read-only)
| Source | Count |
|---|---|
| Collections with a saved location | **0** (column did not exist) |
| Receipt photos with a location | 2 of 3 |
| Staff sign-ins with a location | 246 — 99 in Bengaluru (the admin's computer), 147 near Azamgarh in only **9 spots**, mostly within ~1 km of Azamgarh city (the office) |

So the existing data cannot answer "where are the parties". The app received the phone's location with every new

### 6.3 What was built
- **Storage:** nullable `payment_entries.latitude/longitude` (added automatically by `ddl-auto`, no manual step);
  `PaymentEntryService.tagLocation()` saves a location and ignores missing, out-of-range or 0,0 values. Employee
  and manager add-collection flows call it. `static/js/geo-refresh.js` re-reads GPS when the person starts
  typing so the pin is the party's place, not the office.
- **API:** `CollectionMapController` (**ADMIN only**) → `GET /admin/collection-map/data?from=YYYY-MM-DD`,
  `Cache-Control: no-store`. Returns located collections (own location, falling back to receipt-photo geo), the
  optional login layer (capped at 3,000) and the total collection count.
- **UI:** first built in plain JavaScript, then **rebuilt in React** at the user's insistence, using their two
  supplied components.

### 6.4 React app (`frontend/`)
- Stack: Vite 6, React 18, TypeScript 5.9, Tailwind v4, shadcn-style `components/ui`, MapLibre GL 5,
  supercluster, lucide-react.
- `components/ui/mapcn-marker-content.tsx` (Map, MapMarker, MarkerContent, MarkerTooltip) and
  `components/ui/route-globe.tsx` are the supplied components. The globe's missing helpers were written:
  `route-globe-utils/globe.ts` (land-dot mask from `world-atlas`, rotate/slerp/draw) and `global.css`.
- Design: dark-first, PayTrack indigo + a marigold accent for Azamgarh/selection, Syne + DM Sans + DM Mono,
  glass panels. **Signature element: the direction rose** — 8 petals sized by collections in each compass
  direction from Azamgarh; tap a petal to zoom there.
- Flow: globe intro (arcs from Azamgarh to reference cities) → scales up while the map flies in → pins cluster by
  zoom, colour-coded by collector → detail card (party, amount, date, mode, collector, voucher, coordinates,
  ledger / receipt / Google Maps links). Panel: coverage count, collector filters, sign-in layer toggle, rose,
  searchable party list with "within X m" spread. Phone: draggable bottom sheet. Light/dark theme shares
  `localStorage["paytrack-theme"]`. `?intro=0` skips the globe.
- **Build & deploy:** `cd frontend && npm run build` writes to `src/main/resources/static/js/map-app/` and
  regenerates `templates/admin/collection-map.html` (hashed asset names). **The compiled output is committed**
  so the Render/Docker build stays Maven-only (Node is never on the server; `node_modules` is git/docker-ignored).
  After any frontend change: rebuild, restart Spring (Thymeleaf cache), commit frontend + map-app + template
  together. See `frontend/README.md`.
- Sidebar link "🗺️ Collection Map" (ADMIN only) added to every admin page.

### 10.2 "Website is very slow" — investigation (measured from outside, no prod login)
- Every request has a ~0.5 s floor, even the empty `/health`: the server (Render) and database (Neon) are set up
  for the USA (`render.yaml` names no region → Render's default; Neon is us-east-1) and users are in India.
- Render free tier = 0.1 vCPU and it sleeps when idle (keep-alive covers 6 AM–10 PM IST). The keep-alive hits
  `/health` which deliberately never touches the database, so the free Neon database can still sleep
  (connect after a long idle ~3.6 s vs ~2.4 s warm from here).
- Every static file was served `Cache-Control: no-store` (Spring Security's default), so browsers re-downloaded
  all scripts/styles on every page view.
- Redis was considered and **not** recommended: the app already caches the expensive numbers in memory
  (Caffeine, evicted on writes); the slowness is distance/CPU, a Redis hop adds latency and memory. Its only real
  benefit would be keeping people signed in across restarts.
- Structural fix still open: move Render **and** Neon together to Singapore (moving only one makes it worse).

### 10.3 Browser caching (this commit)
`StaticCacheFilter` + Spring's content-hash resource chain (`spring.web.resources.chain.*`, paths `/js/**`,
`/css/**`): every `th:src`/`th:href` is rewritten to e.g. `/js/theme-<md5>.js` and cached for a year (`immutable`);
the plain names answer `no-cache` (revalidate → tiny 304); icons 1 day; `sw.js`/manifests `no-cache`; pages and
JSON stay `no-store` (live financial data). The Vite-fingerprinted map assets are cached for a year too.
All 139 template links are Thymeleaf links, so all are versioned. Verified: 32 pages across 4 roles render, all
linked assets return 200 with a 1-year cache, plain name gives 304 on a conditional request.

### 10.4 In-app monitoring (this commit)
- `monitoring/RequestMetrics`: in-memory, bounded (≤400 endpoints, 24 hourly buckets each with a 9-bin latency
  histogram, a 60-minute error ring, last 50 server errors). Fed by `RequestTraceFilter`; `/health` and static
  files are excluded. Resets on restart/sleep (no history persisted — not requested).
- **Admin → ⚡ Performance** (`/admin/performance`, ADMIN only; link on every admin page): slowest endpoints first
  (times used, typical, slow case ≈95%, slowest, 4xx, 5xx, last 5xx), summary cards, spike banner, recent server
  errors with their Reference IDs (grep Render logs for the ID). 1 h / 6 h / 24 h windows.
- **Alert:** `ErrorSpikeAlert` checks every minute; ≥ 5 server errors (5xx) within 5 minutes → one bell
  notification (new type `SERVER_ALERT`, 🚨 in the Activity feed) naming the most affected endpoint, then a
  30-minute cool-down. Thresholds in `application.properties` (`monitoring.alert.*`).
- **Neon needs one manual statement** (same pattern as earlier enum additions) before the alert can be stored:
  `ALTER TABLE admin_notifications DROP CONSTRAINT IF EXISTS admin_notifications_type_check; ALTER TABLE admin_notifications ADD CONSTRAINT admin_notifications_type_check CHECK (type IN ('COLLECTION_ADDED','INVOICE_ADDED','VOUCHER_DUPLICATE','VOUCHER_SUSPECT','PARTY_ADDED','VOUCHER_GAP_DIGEST','SERVER_ALERT'));`
  Until it is run, a spike is still counted and shown on the Performance page; only the bell row fails (logged).
- 14 new unit tests (`RequestMetricsTest`, `StaticCacheFilterTest`); all 28 tests pass.
- Tested end to end locally: 7 real 5xx → banner instantly, bell alert after ~1 min with the endpoint named,
  visible in the Activity feed, and a second burst did not alert again (cool-down).
